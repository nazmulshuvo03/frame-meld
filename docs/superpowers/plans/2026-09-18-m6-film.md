# M6 — Film

Real clips per shot, the Final render, and the download. The last milestone in spec §9.

Spec: [`specs/2026-09-09-framemeld-design.md`](../specs/2026-09-09-framemeld-design.md) §4.2,
§5.3, §7, §8 and §9. Predecessor: [`2026-09-18-m5-preview.md`](2026-09-18-m5-preview.md),
whose ledger is [`m5-decisions.md`](../m5-decisions.md).

**Done when:** a user pays credits, waits, and downloads an MP4 assembled from one video
clip per shot.

---

## The honest version of "done when"

Spec §9 words it as "downloads a real AI-generated MP4". M6 builds every part of that
sentence except the AI: `VideoProvider`, the job, the money, the hash chain, the Final
composition and the download are all real, and the clips themselves come from a stub, for
the same reason M5 shipped no Lyria adapter (M5-D2). Wan 2.2 and Veo 3.1 Lite are both paid,
this project's key has no billing, and the codebase already carries two adapters whose
success path has never executed.

So the pipeline is complete and the model is a config line that has never been set. That is
stated here, in the decision record and in the README, rather than buried — a milestone that
claims AI video and ships a colour field would be the worst kind of quiet.

## Decisions taken up front

**M6-D1 — a clip keys on its source still's `content_hash` plus a narrow motion projection.**
`motion_hash_for_shot` is `{motion_prompt, duration_sec}` — exactly what an I2V call takes
besides the image (spec §3.3's `animate(image_url, motion_prompt, duration_sec, params)`).
This is where `motion_prompt` finally earns its column: M5-D5 kept it out of the Preview's
hash because the Preview never reads it, and the same rule now puts it *into* the clip's,
because the clip is the thing it was written for.

Spec §4.1's graph is `shot_image → shot_clip`, so the parent is the still's `content_hash` —
the bytes — not the shot's visual hash. Redrawing a still must re-animate it; rewording the
image prompt without redrawing must not.

**M6-D2 — a clip is refused when the shot has no drawn still, and allowed when that still is
stale.** Refused on missing, because there is nothing to animate; allowed on stale, because
spec §11's whole mitigation for character drift is that "stills are approved before any clip
is generated", and a user animating a still they can see on screen *is* that approval.
Refusing would also make a Meld unfinishable after any upstream edit until every still had
been paid for again.

**M6-D3 — a clip is 80 credits and the Final render is 60.** Spec §7 puts the clips at $6.00
of a $6.90 film and implies $25–30 retail, i.e. 2,500–3,000 credits. 30 clips × 80 = 2,400;
the M3–M5 actions on a 30-shot, 5-character film come to ~514; the Final render at 60 is
§7's $0.20 of render compute at the same ~3× markup the image actions carry. Total ≈ 2,974,
inside the band.

**M6-D4 — still no batch job. N per-shot jobs, one at a time (M4-D5).** The argument is
stronger at 80 credits than it was at 12: one clip failing must refund its own 80 and leave
the other twenty-nine alone, where a batch job has to choose between refunding everything
and charging for nothing.

M3's roadmap expected M6's "resumable render" to be where `settle`'s variable-units path
finally got exercised. It is not, and after four milestones the right conclusion is that it
never will be: every billable action in this product is one indivisible unit of work. The
path stays, because it is the correct implementation of spec §4.3 and removing it would be a
regression against the spec, but it is now a permanent known-unexercised branch rather than
a deferral.

**M6-D5 — the composition's `clip_url` branch lands now.** M5 deliberately left it out
because nothing could produce a clip and an unexercised path inside a renderer is the worst
kind (see the M5-D11 correction). M6 can produce one, so it goes in, and `kind` finally
selects between two real sources exactly as spec §4.2 says.

**M6-D6 — Final renders at 1920×1080**, per spec §3.2's example. `renders.resolution` records
which was used, so a Preview and a Final are distinguishable after the fact.

**M6-D7 — a Final render is refused unless every shot has a clip with bytes.** Same shape and
same reason as M5-D4 and M4-D6: a $24 deliverable with a hole in it is worse than a refusal.

**M6-D8 — the stub video provider emits a real MP4, encoded by ffmpeg.** M4-D8's doctrine for
the third time, and the strongest case yet for it: the bytes are stored as an asset, served
over a signed URL, decoded by Remotion, muxed into a second MP4 and played in a browser. A
placeholder blob would let all five ship broken, and the failure would appear as a black
Final render with every job reporting success.

`imageio-ffmpeg` goes in the **dev** extra and is imported inside the stub, so the day a real
`VideoProvider` is configured the dependency is not in the way. The README's setup already
installs `.[dev]`.

**M6-D9 — `VIDEO_PROVIDER` defaults to `stub`, and no Wan or Veo adapter is written**
(M5-D2's rule, fourth application). See "the honest version" above.

**M6-D10 — download is a `?download=1` flag on the asset route.** The HTML `download`
attribute is ignored for cross-origin URLs, and web and api are different origins, so a
plain link would open the MP4 in a tab instead of saving it. Four lines setting
`Content-Disposition: attachment` with a filename built here, never from user input.

**M6-D11 — clips are driven from the Film page with one batch button, and there is no
per-clip regenerate.** The button queues every shot whose clip is missing or stale, through
the same one-at-a-time drain the Shots page already uses. A per-shot control is a second
copy of `ShotMediaCard` for an action a user takes on the whole film; add one when somebody
wants to redo exactly one clip badly enough to say so.
