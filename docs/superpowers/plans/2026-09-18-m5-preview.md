# M5 — Preview

The scene spec, the Remotion render service, and the first thing in this project a user
can actually watch.

Spec: [`specs/2026-09-09-framemeld-design.md`](../specs/2026-09-09-framemeld-design.md) §3.1,
§3.2, §4.2 and §9. Predecessor: [`2026-09-15-m4-shots.md`](2026-09-15-m4-shots.md), whose
ledger is [`m4-decisions.md`](../m4-decisions.md).

**Done when:** a user with stills and audio presses one button and watches a complete,
watchable draft of their film — animated stills, narration, music — for free.

Same shape as the M4 plan: the decisions, which had to be settled before any code, and the
task order. The code is left to the code. The execution ledger will be `m5-decisions.md`.

---

## Decisions taken up front

**M5-D1 — asset URLs are HMAC-signed, and storage stays local disk.**
The render service has no database, no session and no cookie (spec §3.1), so it needs URLs
it can simply GET. M3-D1 deferred S3/R2 "until something outside the api needs to read a
file, which is M5's render service" — that moment has arrived, and R2 is still not the
answer to it. A presigned S3 URL needs an account, credentials and egress billing, none of
which exist here; what the render service actually needs is a URL that works without a
cookie, which is an HMAC over the existing `/assets/{id}` route and about twenty lines. The
`Storage` protocol is untouched, so the R2 implementation stays a later, independent swap
rather than a prerequisite for watching a film.

The signature is scoped to one asset id and carries an expiry, so a leaked URL is a leak of
one file for one hour, not of a user's library. `ASSET_SIGNING_SECRET` has no default: a
signing key with a default is a signing key everybody has.

**M5-D2 — music is a stub provider only. No Lyria adapter.**
Spec §6.3 names Lyria as M5's music default and marks it paid. This project's Gemini key has
no billing enabled — M3's probe found that, M4 confirmed it — so a Lyria adapter could not be
called even once. The codebase already carries two paid adapters that have never made a
successful call (`GeminiImageProvider`, `GeminiSpeechProvider`); a third, written blind
against a documented response shape, would be the same mistake for the third time and would
make the *third* "verify before trusting it with a user's credits" line in the README.

`MusicProvider` (spec §3.3's fifth adapter) and a stub land. The stub emits a real WAV
(M4-D8's rule), because the duration reader, the asset row, the mixer and the browser all
treat it as audio. M5's declared AI spend is ~$0, and this is what that means.

**M5-D3 — the music prompt is derived, not authored, and gets no new column.**
Built from the Meld's `style_preset` and its scene headings, plus the film's total running
time. A `music_prompt` column would be a field the user has to fill in before they can hear
anything, on the one milestone whose point is that the first watchable draft is one click
away. Hashed as a narrow projection like every other input (M4-D2's rule), so re-heading a
scene re-scores the film and editing an image prompt does not.

**M5-D4 — a Preview is refused when any shot has no fresh still.**
422, naming how many are missing, before any job row exists. Same shape and same reason as
M4-D6: a film with holes in it is not the deliverable the user asked for, and the only
repair is to notice, fix and render again. A shot with *no audio* is not refused — a shot
with no line is a correct shot, and silence over it is the right answer.

**M5-D5 — motion is derived from the shot, and `motion_prompt` is deliberately not read.**
The Ken Burns from/to is computed from `camera` and `order_index`: an establishing shot
pushes in slowly, a close-up drifts, and alternating shots pan opposite ways so a cut never
looks like a jump. `motion_prompt` is prose written for an image-to-video model (spec §8) and
parsing it into a pan would be guessing. It is therefore not in the render's input hash
either, which is the narrow-projection rule applied honestly: a field the render never reads
must not invalidate a render.

**M5-D6 — Preview renders at 1280×720, 30 fps.**
Spec §4.2 makes Preview the cheap iteration gate; 720p halves the render time for a draft
nobody ships. The spec's §3.2 example shows 1920×1080, which is Final's resolution and
arrives with M6. `renders.resolution` records which was used, so the two are distinguishable
after the fact.

**M5-D7 — the Preview render takes no hold and has no quote.**
Spec §4.2 and §9 both say Preview is free, and it is free for a reason: it is the approval
gate that makes a $6 Final render humane. Charging for it would defeat the thing it exists
for. The job row carries `credits_held = 0` and no ledger row is written at all — a zero
hold would put a zero-delta line in a ledger a human has to be able to read.

What stops a script pressing the button thirty thousand times is the mechanism that already
exists: the render's `input_hash` is the idempotency key, so a second press with nothing
changed is a cache hit that starts no work. Re-rendering requires actually changing
something.

**M5-D8 — `renders.input_hash` is computed over the spec with content hashes where the URLs
go.** A signed URL carries an expiry, so hashing the document as sent would make every render
unique and the cache would never hit — the same self-invalidating shape as M4's casting bug,
arrived at from the other direction. The assembler therefore produces two documents from one
walk: the render JSON, with signed URLs, and the hash payload, with each artifact's
`content_hash` in the same position.

**M5-D9 — the render service keeps finished files in a temp directory and serves them from
`GET /render/{id}/output`.** It has no database and no storage credentials (spec §3.1), and
the only consumer is the worker, which downloads the MP4 once and stores it as an asset. A
file left behind by a crash is garbage on a disk nobody backs up, which is the cheapest
possible failure mode.

**M5-D10 — the worker polls the render service inside the job.** Spec §3.1's two endpoints
are asynchronous by design, and the thing that waits is the arq job. A job row already
carries state, attempts, an error and a failure path; a second async state machine layered on
top of it would be two things to keep true and one of them would be wrong.

**M5-D11 — one Remotion composition serves both kinds (spec §4.2).** `kind` picks whether a
shot's visual source is its still plus motion, or M6's clip. That is the whole difference,
and it is what makes Preview cheap to have built.

**M5-D12 — music is one track across the whole film, ducked under the speech.**
`music_url` is at the top of the scene spec (§3.2), not per shot, so Remotion lays one
`<Audio>` over the timeline. A fixed −18 dB under narration rather than sidechain ducking:
the fancier version is a mixing feature, and this milestone's job is that the draft is
watchable.

## Tasks

1. `models/render.py`: `Render`, `RenderKind`; migration (hand-checked).
2. `assets/signing.py`: HMAC sign and verify; the asset route accepts a signature *or* a
   session.
3. `providers/music/`: protocol, stub, registry; `rates.py` gains a music table.
4. `render/spec.py`: the scene spec, its motion derivation and its hash payload.
5. `render/client.py`: the two-endpoint HTTP contract, as a protocol with a stub.
6. `render/service.py`, `schemas.py`, `router.py`: music and preview requests.
7. Worker: `generate_music`, `render_preview`.
8. `staleness.py`: music clips and renders join the walk.
9. `credits/pricing.py`: `generate_music` only (M5-D7).
10. `services/render/`: the Node service — `node:http` server, Remotion composition, bundler.
11. Backend tests.
12. Web: Film page, API client.
13. Frontend tests.
14. Verification, `m5-decisions.md`, README, spec corrections.
