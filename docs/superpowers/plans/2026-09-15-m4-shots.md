# M4 — Shots

Shot stills conditioned on character sheets, speech per shot, and the first multi-parent
hash in the system.

Spec: [`specs/2026-09-09-framemeld-design.md`](../specs/2026-09-09-framemeld-design.md) §9.
Predecessor: [`2026-09-13-m3-cast.md`](2026-09-13-m3-cast.md), whose "What comes after"
section named the five decisions this milestone had to make. All five are answered below.

**Done when:** every shot has a still whose characters visibly match their sheets, plus an
audio clip; editing a character marks exactly the right stills stale and nothing else.

This plan is deliberately shorter than its predecessors. M1–M3 were written to be handed to
a separate executing session, so they transcribed every file in full. This one was written
and executed in one sitting, so it carries the decisions — which are load-bearing and had to
be settled before any code — and the task order, and leaves the code to the code. The
execution ledger is [`m4-decisions.md`](../m4-decisions.md).

---

## Decisions taken up front

**M4-D1 — `shot_characters` is populated by its own job kind, `map_shot_characters`.**
M3-D2 deferred this table on the grounds that populating it needs an LLM pass mapping the
cast onto the shot list. That pass now exists as a first-class artifact: its own job kind,
its own `input_hash`, its own price, its own button.

The two alternatives were both worse. Folding it into `generate_characters` would make the
cast job depend on shots existing, and would leave a script regeneration — which cascades
the shots away, and the join rows with them — repairable only by re-running cast extraction,
which deletes every sheet the user paid for. Folding it into the shot-image job is
impossible: `input_hash` must be computable *before* the job runs, and this mapping is the
job's output.

The same pass also writes `shots.speaker_character_id`, which has existed since M2 with
nothing to set it. It is the only pass that holds both halves of that fact.

Cost: one migration widening the `job_kind` CHECK, because spec §5.4's job list does not
contain this kind. The spec is corrected in place, as M3 corrected §9.

**M4-D2 — a shot still's `input_hash` keys on a narrow *visual* projection of the shot, plus
the sorted `content_hash` of every character sheet it references.**

The multi-parent half is spec §4.1, verbatim: the hash includes the `content_hash` of every
`character_image` used as a reference and of the shot it depicts. Sorted, so the order the
references happened to be loaded in cannot change the hash.

The narrow half is M3's most expensive lesson repeating. A shot's `content_hash` covers
`motion_prompt`, `duration_sec`, `speech_text`, `dialogue_kind`, `speaker_character_id` and
`order_index` — none of which the image prompt uses. Keying a still on all of it would mean
editing the spoken line invalidated the picture, which is exactly the bug the M3 browser pass
found for character sheets. `visual_hash_for_shot` is `{image_prompt, camera}` and nothing
else. Widen it the day the still prompt reads another field.

**M4-D3 — speech keys on its own narrow projection, and `characters.voice_id` becomes a
user-editable field.**

`speech_hash_for_shot` is `{speech_text, dialogue_kind, voice_id}`. Editing the image prompt
must not cost the user an audio clip, and re-recording a line must not cost them a picture.
The two projections are disjoint, which is the point.

`voice_id` has existed on `characters` since M3 with nothing to set it, and it is already
inside `content_hash_for_character` and deliberately outside `visual_hash_for_character` —
so changing a character's voice invalidates their dialogue and not their sheet, for free,
with machinery that already exists. It becomes a `<select>` on the character card, seeded at
extraction time with a deterministic pick from the provider's voice list.

**M4-D4 — `audio_clips` lands in full per spec §5.3; only shot-owned narration and dialogue
are produced.** `owner_type`/`owner_id` are polymorphic and `kind` declares `music` and
`sfx`, neither of which M4 generates. Same trade as `CharacterImageKind` in M3: declaring an
enum value costs nothing now and an `ALTER` later.

**M4-D5 — no batch job. "Generate all" is N ordinary per-shot jobs, run one at a time.**
M3's roadmap expected this to be where `settle`'s variable-units path finally got exercised.
It is not, and that is the better answer: one job per shot means a shot that fails refunds
its own credit and the other twenty-nine still have their pictures, where one batch job has
to choose between refunding everything and charging for nothing. That choice is a
resumable-job design, it belongs to M6's thirty clip generations, and buying it here would
be paying for it twice.

The page holds a queue of pending shot ids and runs them through the existing single-job
polling hook one at a time. That also rate-limits the provider for free.

**M4-D6 — a still is refused when a character in the shot has no sheet.** 422, naming who is
missing, before any hold. Generating it anyway would produce the drifting face that spec §11
lists as a high-severity risk, and would leave the staleness arithmetic wrong — a shot whose
ref list is missing a character cannot go stale when that character changes. A shot with no
characters at all (an insert, an establishing shot) generates with no references, which is
correct rather than a special case.

**M4-D7 — `update_shot` recomputes staleness.** It did not, because until now nothing
depended on a shot's content. The identical omission in `update_character` was the M3 browser
pass's first finding; this is the same bug, found by reading rather than by clicking.

**M4-D8 — the stub speech provider emits a real WAV.** Same doctrine as M3's `solid_png`: the
duration reader, the asset row and the browser's `<audio>` element all treat this as audio, and
a stub returning `b"not-audio"` would let all three ship broken. Duration comes from stdlib
`wave`, which is the audio sibling of `png_dimensions`' eight lines of `struct`.

**M4-D9 — `SPEECH_PROVIDER` defaults to `stub`.** As `LLM_PROVIDER` and `IMAGE_PROVIDER` do,
for the same reason: the suite and the app run with no key and no network.

**M4-D10 — reference sheets are read from storage per call, with no cache.** A shot with four
characters is four `Storage.get` calls. M3's roadmap flagged this as "worth a cache, and worth
measuring before building one". It has not been measured, so there is no cache.

## Tasks

1. Models: `shot_characters`, `shot_images`, `audio_clips`; `MAP_SHOT_CHARACTERS` job kind.
2. Migration (hand-checked, per Global Constraints — autogenerate is read, not trusted).
3. `shots/hashes.py`: `visual_hash_for_shot`, `speech_hash_for_shot`,
   `shot_characters_input_hash`, `shot_image_input_hash`, `audio_clip_input_hash`,
   `content_hash_for_shot_image`, `content_hash_for_audio_clip`.
4. `providers/speech/`: protocol, voice list, stub, Gemini adapter, registry.
5. `assets/service.py`: `wav_duration`, and `duration_sec` on the asset row.
6. `shots/casting.py`: the mapping prompt, schema, parser and applier; stub LLM branch.
7. `shots/service.py`, `schemas.py`, `router.py`.
8. Worker: three new tasks.
9. `staleness.py`: stills and audio join the walk.
10. `credits/pricing.py`: three new quotes.
11. Backend tests.
12. Web: Shots page, `ShotMediaCard`, voice select on the Cast page, API client.
13. Frontend tests.
14. Verification, `m4-decisions.md`, README, spec corrections.
